Overview

0.1.0-foundation is the first playable code milestone of starbase-builder: a single-file, map-first base builder set at Earth Starbase. The player places a tiny industrial site on green grass, watches resources and simple production tick, moves one stack placeholder between bay and pad, and runs a crude static fire that couples propellant, pad, and a short visual effect.

This milestone is deliberately small in systems, but architecturally honest about the long-term Starbase model: realistic component catalog, process chains, and a locked Visual Upgrade Rule so every future improvement has a physical silhouette change on the map—not invisible stat bumps.

Product distinction vs starship-dev: starship-dev is a dark, dashboard-first flight/ops slice. Starbase-builder is an earthy AoE-style living industrial site where pad, tank farm, bay, factory, power, and (later) roads/vehicles/workforce work together. Flight is the pulse; the base is the body.

Product guide (locked — rev 4)

North star of the project (not just 0.1.0): build a simple, quick-to-finish game even in its finished state. The joy is the ride — watching a real industrial spaceport’s components, processes, and visual cues click together. Depth comes from realism of mechanics, not from endless systems or grind.

  • Compact complete game — a full playthrough should feel complete in a short session once content is finished. No sprawling empire sim.
  • Super realistic processes — pad, propellant, bay, factory, stack, static fire, hop, orbit, recover… modeled the way the industry actually works, even when simplified numbers.
  • Visual cues that tell the truth — every upgrade changes the object on the map in a physically sensible way (Visual Upgrade Rule).
  • Reality ladder — content order follows how reality works: resources & infrastructure first → stack & load → static fire / hop → harder flight → recovery → cadence → outer sites later. Improve Starbase mechanics over time by going down that ladder (deeper fidelity), not sideways into unrelated minigames.

Play order for 0.1.0 (first playable): (1) Place components that generate / hold resources → (2) form a basic ecosystem so resources grow → (3) put a stack on a pad and get a basic launch-adjacent event (static fire in 0.1.0; hop next) → (4) spend surplus to improve pad / site slightly with visible change. Full Starbase depth comes later along the same ladder.

Rev 4 does not throw away TUNING/PR plan; it re-emphasizes start order and the compact-game goal. Implementation of index.html first draft should make resource generation and the closed loop obvious before any extra chrome.

Background & Motivation

Why this game exists

  • Watch a real industrial spaceport grow under the player’s hands.
  • Launch and recover with increasing cadence, then unlock orbit → Moon → Mars without making Earth Starbase obsolete.
  • Sites accumulate; outer bases depend on Earth production and reliability.

Why Foundations starts tiny

The project philosophy is start super simple, accumulate. Complex rendering, contracts, finance rounds, full phase odds, and multi-site logistics are proven or sketched (starship-dev harvest + thematic arc) but must not block a green-map dopamine loop:

  1. Place buildings that look like a base.
  2. See resources move because buildings exist.
  3. See one physical upgrade change the map.
  4. Fire engines once so systems feel coupled (static fire in 0.1.0).

Goals & Non-Goals

Goals (0.1.0)

  1. Ship a runnable index.html playable in a browser without build tools.
  2. Render an earthy grass + dirt map with pan and light zoom.
  3. Support ≤4 placeable types: Orbital Pad (OLM stub), Mega Bay, Tank Farm, Starfactory.
  4. Implement resources: Steel, Methane (ch4), LOX, Power (display), Day tick.
  5. Place buildings on valid terrain; spend Steel; show selection + inspector.
  6. Passive production (Starfactory steel drip; Tank Farm propellant fill) so the site feels alive.
  7. One stack placeholder with bay → pad logistics (authoritative vehicle location model).
  8. Prove the Visual Upgrade Rule with Pad L1 → L2 (wider trench / taller OLM).
  9. Static fire (must-have): spend propellant, short crude flame on pad, event log — closed-loop proof of Pad ↔ Tank Farm ↔ Stack.
  10. Document north-star domain model so later milestones extend data, not rewrite fiction.
  11. Soft objective checklist / empty-state hints so first session has a goal after placement (PR8).

Non-Goals (0.1.0)

  • Moon / Mars / multi-site
  • Full mission ladder, phase odds, contracts, debrief modals
  • Finance rounds, credits economy
  • Chopsticks catch, hop trajectory, orbital flight sim
  • Workforce, housing, city, land purchase
  • Grok Imagine assets, audio suite, day/night lighting
  • Dark starship-dev HUD
  • Multiplayer, accounts, server
  • Splitting into modules / build pipeline
  • Perfect isometric math or 3D engines
  • Power throttling production (Power is display-only)
  • Zone-based steel discounts or hard zone blocking (except water)
  • Save/load (deferred; no localStorage required)
  • WDR UI (process ID reserved only)

B. Visual Upgrade Rule (locked principle)

Rule — Visual Upgrade Rule (VUR):

Every level of every placeable must change at least one of: silhouette, footprint, or clear secondary geometry readable at default zoom.
Upgrade UI copy leads with the physical change, then may list mechanical effects.
Pure “+12% reliability” with identical sprites is forbidden.

Acceptance for Pad L1 vs L2: human screenshots side-by-side in PR6 (or notes in PR description); difference must be obvious without reading numbers (wider trench + taller OLM).

Inspector pattern:

Next upgrade — Pad L2: “Widen flame trench & raise OLM”
• Visual: trench wider; OLM block taller
• Effect: static fire costs 10% less propellant
Cost: 40 Steel

Intended first-session build order (tutorial path)

Suggested order (also fine if player deviates — any order of the four placeables works):

  1. Starfactory (40) — steel production online early (habit for later milestones).
  2. Tank Farm (30) — Methane/LOX begin filling.
  3. Mega Bay (35) — integration slot ready.
  4. Orbital Pad (50) — launch complex ready.
  5. Select Mega Bay → Build stack (15).
  6. Select Pad → Send to pad (0 steel).
  7. Select Pad → Upgrade to L2 (40) — VUR proof.
  8. Static Fire when Methane/LOX ≥ 10 (tanks fill in ~1 game day from 20 start).

Palette may still list Pad first (mock order); UI should not force order. Optional PR8 hint: “Tip: build Starfactory early so steel keeps flowing.”

Static fire formula:

need: stack on selected pad AND ch4 >= SF_CH4_NEED AND lox >= SF_LOX_NEED AND !fxActive
mult = pad.level >= 2 ? SF_PROP_MULT_L2 : 1.0
spendCh4 = ceil(SF_CH4_SPEND * mult)
spendLox = ceil(SF_LOX_SPEND * mult)
// always "success" in 0.1.0 — no RUD RNG

Power (locked): Display-only bar at 100%. Do not implement −1%/day or production throttle. UI may show “Power 100% (grid stable)” so the slot exists for later power_node.

Capacity stacking:

function sumCap(state, kind /* 'ch4'|'lox' */) {
  let cap = 0;
  for (const b of state.site.buildings) {
    if (b.type !== 'tank_farm') continue;
    const eff = BUILDING_DEFS.tank_farm.levels[b.level].effects;
    cap += kind === 'ch4' ? eff.ch4Cap : eff.loxCap;
  }
  return cap;
}

Fill each day: for each tank farm, add fill rates, then clamp site totals to sumCap.

C.6 Stack location — single source of truth (locked)

Invariant:

  1. **vehicle.buildingId is authoritative** for where the stack is.
  2. building.stackId is a denormalized cache updated only inside assignStack(vehicleId, buildingId) / clearStack(buildingId).
  3. On load or debug assert: every building.stackId matches the vehicle that points at it; at most one vehicle; MAX_STACKS === 1.
  4. **No locationKind / in_transit in 0.1.0.** Derive UI location for display:
  • if host.type === mega_bay → “At Mega Bay”
  • if host.type === pad_orbital → “On pad”
  1. Vehicle status is always 'ready' in 0.1.0.
function assignStack(state, vehicleId, buildingId) {
  const v = getVehicle(state, vehicleId);
  if (v.buildingId) {
    const prev = getBuilding(state, v.buildingId);
    if (prev) prev.stackId = null;
  }
  const b = getBuilding(state, buildingId);
  // if b.stackId set and !== vehicleId → reject
  v.buildingId = buildingId;
  b.stackId = vehicleId;
}

C.7 Playtest success criteria (human, &lt;3 minutes)

All of the following are required to accept 0.1.0-foundation:

  1. See green map, token-correct chrome, resource bar with live Steel/Methane/LOX/Power/Day.
  2. Place all four building types in any order (steel decreases; START_STEEL=220 prevents softlock; max one of each).
  3. Watch Steel rise (factory) and Methane/LOX fill (tanks).
  4. With Starfactory present, build prototype stack at bay (15 steel); send to pad; see capsule move.
  5. Upgrade pad L1→L2; screenshot-obvious wider trench + taller OLM.
  6. Static fire: spend propellant, see flame ~0.5s, log success; L2 spends 9/9 if upgraded.
  7. Objective checklist completable (PR8 polish).

function onGameDay(state) {
  const r = state.site.resources;
  for (const b of state.site.buildings) {
    const eff = BUILDING_DEFS[b.type].levels[b.level]?.effects;
    if (!eff) continue;
    if (b.type === 'starfactory') r.steel += eff.steelPerDay;
    if (b.type === 'tank_farm') {
      r.ch4 += eff.ch4FillPerDay;
      r.lox += eff.loxFillPerDay;
    }
  }
  r.ch4 = Math.min(sumCap(state, 'ch4'), r.ch4);
  r.lox = Math.min(sumCap(state, 'lox'), r.lox);
  r.day += 1;
}

E.1 Single-file structure (implementer note)

Suggested section order inside index.html:

  1. <head> Tailwind CDN + minimal CSS (tokens, canvas fill)
  2. HTML chrome (top / left / canvas host / right / bottom log)
  3. <script>: // --- constants & TUNING ---
  4. // --- BUILDING_DEFS ---
  5. // --- state ---
  6. // --- pure helpers (grid, sumCap, zoneAt, canPlace, countType, assignStack)
  7. // --- simulation (onGameDay, tryStaticFire, tryUpgrade)
  8. // --- render (drawMap, drawBuilding, drawFx) via rAF
  9. // --- input (pointer, wheel, buttons)
  10. // --- boot init state + listeners

Loop: one requestAnimationFrame for draw + input coalescing; day clock uses performance.now() delta into dayAccumMs (not one setInterval that desyncs when tab is backgrounded — still OK to use rAF-only accumulation).

FPS budget: target 60; 0.1.0 content is trivial (&lt;50 draw calls). No particle pool required.

Offline: Tailwind CDN required for 0.1.0 chrome styling; offline without CDN yields unstyled DOM but canvas map can still run if JS loads. Document in README when shipping. No SRI pin required for prototype CDN script (known tradeoff).

Growth: keep file under ~1.5–2k lines before requesting split approval; use section banners.
